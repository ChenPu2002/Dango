# 记忆与提炼机制 · 设计汇报

## TL;DR（回答三个问题）

| 问题 | 回答 |
|---|---|
| 卡片更新是自动的吗？ | **是**。事件驱动：停止录音 → 自动 ASR → 提炼 → 发布订阅刷新全部页面。无任何手动步骤，真机已验证（19 秒录音 → 11 秒处理 → 卡片/待办/心情/今日四页自动出现新内容） |
| 有没有设计良好的记忆机制？ | **目前没有，这是当前最大的设计短板**。现在的提炼是无状态、一次性的：每条录音独立处理、结果盲目追加，互相之间没有任何联系 |
| 反复追加新内容，能实时更新吗？ | **能，但必须把"追加式"改成"合并式"**（本方案核心）。停止录音后约 15~25 秒内，旧卡片被订正/去重、新卡片生成、画像更新，全页自动刷新 |

---

## 一、现状剖析

### 已具备（机制层）
```
停止录音 ─→ 自动入队 ─→ ASR(火山) ─→ 提炼(DeepSeek) ─→ 写入 store ─→ 发布订阅 ─→ 四页自动刷新
   事件触发      状态机        转写          结构化JSON      本地持久化      <100ms         无需手动
```

### 不具备（记忆层）——反复追加场景下会暴露 5 个问题

| # | 问题 | 表现 | 举例 |
|---|---|---|---|
| 1 | **卡片重复** | 同一知识点每条录音都生成新卡 | 周一"泰勒公式是什么"，周三又生成一张一模一样的 |
| 2 | **知识碎片** | 永远是孤立条目，不聚合成课程级体系 | 两节课都讲泰勒，产生 6 张卡+2 条时间线，但没有"高数·第三章"的知识文档 |
| 3 | **无冲突订正** | 老师改口/作业变更无法更新旧内容 | 录音说"作业改成第 2 题"，旧卡片上还是第 1 题，且永远没人改它 |
| 4 | **待办重复** | 同一约定被多次提起就生成多条 | "周五交大纲"说两遍 → 两条待办 |
| 5 | **无用户画像** | LLM 每次都是"陌生人" | 不知道你在上哪些课、常跟谁一起、考试什么时候，提炼质量无法个性化 |

另外存在一个工程隐患：**当前多条录音会并发处理**，将来做合并时会产生读写竞态（两个 job 同时读旧卡片、互相覆盖）。

## 二、设计方案：三层记忆 + 合并式提炼

### 2.1 总体架构

```
新录音 ─→ ASR ─→ ① 提取（工作记忆 L1：本条的结构化结果）
                        │
                        ▼
              ② 合并引擎（第二次 LLM 调用，携带旧记忆上下文）
                 输入：新提取 + 活跃卡片清单 + 课程笔记摘要 + 用户画像
                 输出：操作指令（不是内容本身）
                 { cards:    { add[], update[{id,新答案,理由}], archive[] },
                   todos:    { add[], update[], done[] },
                   note:     { course, patch段 },
                   profile:  { 增量画像更新 } }
                        │
                        ▼
        L2 知识层（卡片/课程笔记，带版本与状态）   L3 画像层（滚动摘要）
                        │
                        ▼
                 发布订阅 → 各页实时刷新（现有机制复用）
```

关键转变：**卡片的产出从"内容"变成"操作"**。LLM 不再直接吐新卡片，而是吐"对现有记忆做什么"——新增、订正、归档、合并。

### 2.2 工作记忆（L1）
- 即现有 pipeline 的单条提取结果，用完即归档进时间线
- 保持无状态，职责单一：忠实转写本条材料

### 2.3 知识层（L2）——核心：卡片是"演化"的，不是"堆叠"的

**卡片实体扩展：**
```js
{ id, q, a, topic: "高数·第三章",        // 课程/主题归属
  status: "active" | "superseded" | "archived",
  version: 3, updatedAt, history: [{a, at, reason}] }  // 订正版本链
```

**合并规则（写进 prompt 的硬约束）：**
1. 新卡与现有活跃卡**同义**（问的是同一知识点）→ 不新增，走 `update`（可选补充答案）+ 复习权重 +1
2. 新信息**订正**旧答案（"作业改成第2题"）→ `update` 旧卡，旧答案进 history，卡片页显示「已订正」角标
3. 新卡确实是**新知识点** → `add`
4. 被完全覆盖的旧卡 → `archive`（不删除，复习页不再出现）
5. 待办同构：同约定合并；录音里说"交了/取消了" → `done`/`archive`

**课程笔记（活的文档）：** 每门课一份滚动笔记，合并引擎输出 `patch` 段落追加，今日页的时间线是"事件流"，课程笔记是"知识沉淀"——两个视角。

**去重实现路径（不引入新依赖起步）：**
- 阶段一：把活跃卡片压缩成 `id + 问题 + 答案前40字` 清单塞进合并 prompt，由 LLM 判断同义/冲突（卡片 ≤ 200 张时完全够用，deepseek-flash 1M 上下文无压力）
- 阶段二（规模大了再上）：embedding 召回 top-20 相似卡 → 只把这 20 张给 LLM 精判，prompt 长度恒定

### 2.4 画像层（L3）
- 滚动摘要一份：课程与考试节点、常出现的人（小鹿）、作息、情绪基线、近期目标
- 更新时机：每天最后一条 job 完成后 rollup 一次（也可手动触发）
- 用途：
  - 给下一次提取/合并提供上下文（提炼质量随使用越来越准）
  - 「今日拾光」从模板文案变成真实生成
  - 考试倒计时、周期性提醒的数据来源

### 2.5 实时性与工程保障

**时延预算（停止录音后）：**

| 阶段 | 耗时 | 说明 |
|---|---|---|
| ASR | 4~10s | 随音频时长 |
| ① 提取 | 5~8s | 现有 |
| ② 合并 | 3~5s | 新增一次 LLM 调用 |
| UI 刷新 | <100ms | 发布订阅，已具备 |
| **合计** | **15~25s** | "停止后半分钟内全页更新" |

**串行队列（必须改）：** 多条录音连续进来时，job 从并发改为**串行队列**逐条走完整链路（提取→合并），保证合并引擎看到的旧记忆是上一个 job 提交后的状态，消除竞态。排队状态在"处理动态"里已有展示，体验上无感。

**失败兜底：** 合并失败不影响主链路——降级为现在的直接追加（当前行为），卡片页照常可用，下一条录音的合并会再尝试收敛。

## 三、成本估算（单条 1 分钟录音）

| 调用 | 输入规模 | 说明 |
|---|---|---|
| ASR | 1 分钟音频 | 按火山计费 |
| 提取 | 转写文本 ≈ 300 字 | 一次调用 |
| 合并 | 新提取 + 卡片清单（100张 ≈ 4k tokens）+ 画像摘要 | 一次调用 |

比现状多 **1 次 LLM 调用**，换来记忆不重复、可订正、可积累。

---

## 四、实施范围（确认后一次做完）

1. `store`：卡片/待办实体扩展（topic/status/version/history）、新增 courseNotes、profile
2. `pipeline`：并发改串行队列；新增合并引擎步骤（含失败降级）
3. UI：卡片页「已订正」角标与版本链查看、今日页画像摘要区、心情页趋势标签
4. 真机回归：复用现有 adb 自动化流程（录音→播语音→验证四页刷新）
